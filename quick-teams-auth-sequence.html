Authenticating an HR Buddy conversation in Microsoft Teams

Two views of the same rollout: the one-time trust configuration between Okta, AWS, and Amazon Quick, and the live request path every time an employee messages the agent inside Teams.

Okta AWS (IAM Identity Center / Secrets Manager / IAM) Amazon Quick Microsoft Teams

Stage 1 — One-time trust setup

Performed once by three different admins before any employee can use the Teams extension. Nothing here runs per-conversation — it establishes the trust chain that Stage 2 relies on for every message afterward.

    Note over OA,OK: Okta App Integration
    OA->>OK: Create OIDC App Integration (Web Application)
    OA->>OK: Enable grant types — Authorization Code + Refresh Token, Implicit (hybrid)
    OA->>OK: Add callback URI per AWS region
    OA->>OK: Assign controlled access + enable Federation Broker Mode
    OK-->>OA: Issues Client ID and Client Secret
    end

    rect rgb(252, 244, 230)
    Note over AA,IC: Establish trust in AWS
    AA->>IC: Create Trusted Token Issuer (Issuer URL = Okta OIDC endpoint)
    AA->>IC: Map Identity Provider attribute + IAM Identity Center attribute = Email
    IC-->>AA: Returns Trusted Token Issuer ARN
    AA->>SM: Store Okta client_id + client_secret as a secret
    SM-->>AA: Returns Secret ARN
    AA->>IR: Create IAM role — trust policy scoped to Quick's regional service principal
    AA->>IR: Attach inline policy — secretsmanager:GetSecretValue, sso:DescribeTrustedTokenIssuer
    IR-->>AA: Returns Role ARN
    end

    rect rgb(232, 245, 242)
    Note over QA,Q: Configure Quick
    QA->>Q: New extension access → enter Trusted Token Issuer ARN + Aud claim (Okta Client ID)
    QA->>Q: Select Microsoft Teams → enter M365 Tenant ID, Secrets Role ARN, Secrets ARN
    QA->>Q: Deploy extension → bind to HR Buddy agent
    end

    rect rgb(241, 236, 249)
    Note over MA,T: Microsoft 365 approval
    MA->>T: Open install link, review permissions
    MA->>T: Grant admin consent for Amazon Quick app
    MA->>T: Optional — scope availability to a pilot user group
    end

    Note over OA,T: Trust chain now exists — repeat for future extensions is not required
Why this matters: every arrow in this stage happens exactly once per organization. If any single link breaks — a missing grant type in Okta, a mistyped issuer URL, a role trust policy scoped to the wrong region — Stage 2 fails silently for every employee, not just one. This is the sequence worth walking a security reviewer through before go-live.

Stage 2 — Runtime flow: an employee sends a message

This is what happens, end to end, every single time an employee messages HR Buddy in Teams — whether or not they've ever used Quick before.

sequenceDiagram
    autonumber
    participant E as Employee
    participant T as Microsoft Teams
    participant QX as Quick Teams Extension
    participant IR as IAM Role
    participant SM as Secrets Manager
    participant IC as AWS IAM Identity Center
    participant OK as Okta
    participant QR as Quick Agent Runtime
(Quick Index + HR Buddy)

    E->>T: Opens Teams (already signed in — Okta session federated into Entra ID)
    E->>T: Sends message to "Amazon Quick" (direct message)
    T->>QX: Forwards message + employee's Entra ID token

    QX->>IR: AssumeRole (STS)
    IR-->>QX: Temporary, narrowly-scoped credentials

    QX->>SM: GetSecretValue (Okta client_id / client_secret)
    SM-->>QX: Returns stored Okta credentials

    QX->>IC: Present employee token for exchange
(references configured Trusted Token Issuer, checks Aud claim)
    IC->>OK: Validate token signature against Okta's trusted issuer keys
    OK-->>IC: Signature valid — issuer confirmed
    IC-->>QX: Identity resolved (matched by Email attribute)

    QX->>QR: Does a Quick user exist for this email?
    alt No existing Quick user
        QR->>QR: Just-in-time provisioning — RegisterUser
(created at the account's configured subscription tier)
    else User already exists
        QR->>QR: Load existing user record
    end

    QX->>QR: Route request to the linked agent (HR Buddy)
    QR->>QR: Retrieve from linked knowledge base (Quick Index semantic search)
    QR->>QR: Generate grounded, cited response
    QR-->>QX: Returns response
    QX-->>T: Delivers response
    T-->>E: Displays answer in the chat
Two things worth calling out to stakeholders: first, the employee never sees a separate login — every credential exchange above happens silently between Stage 1's already-established trust chain. Second, the "just-in-time provisioning" branch only fires the very first time a given employee ever messages the bot — from then on, every future message skips straight to the existing-user path, but the identity verification (steps 4–11) still runs in full on every single message, not just the first.
STEPS 1–3

Employee-side trigger

No separate Quick login — the employee's existing Teams/Entra session is what gets forwarded.

STEPS 4–7

Credential retrieval

Quick's backend assumes its scoped IAM role and pulls the Okta app secret needed to complete the identity exchange.

STEPS 8–11

Identity verification

IAM Identity Center calls back to Okta to confirm the token's signature against the trusted issuer, then resolves it to a specific person by email.

STEPS 12–17

Provisioning & response

A Quick user is created automatically if needed, then the request is routed to HR Buddy for retrieval and generation.
